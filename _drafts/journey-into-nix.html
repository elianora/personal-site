I am going to lead this post off with a brief description that may help you decipher if this post is for you or not. If the following describes your use case, you can have a solid idea of whether there is value in proceeding:

"I want to use a declarative, functional programming language to control the software installed across one or more of my machines, which will result in all machines involved having any version of any software pinned to identical states to ensure reproducibility and consistency."

If that doesn't sound appealing or is unclear to you, this may not be the post for you, and that's fine - this is going to be a step through the basics as I learned them to recently configure all of my systems, including some things I learned the hard way and have smoothed out to write this.

What Are Nix, Nixpkgs, and NixOS?

So, let's get started - to really understand the value of these tools, first you have to actually define what they are and are not. If you'd like something that explains this better than I can, this video by Surma is an excellent resource! If you watch the video, feel free to skip this first section.

Nix is:

  • A domain-specific programming language that is declarative, functional, dynamically typed, and lazily evaluated, inspired by Haskell as described in Eelco Dolstra's PhD thesis
  • Meant to express immutable operating system state
  • Going to treat file and system paths as first-class citizens
  • Going to place file and system paths in a store, with files in their ordinary location being replaced by symbolic links to that store
  • Going to track the hashes of any resulting output so that dependencies more reliably can be considered identical and atomic across multiple systems, allowing for simple system rollbacks

Nix is not:

  • A system with a simple command-line tool for installing packages permanently
  • A package manager in the traditional sense, as it seeks to avoid the pitfalls of common package management solutions such as binaries or build instructions with no guarantee of consistent tooling
  • Mutable by default - all Nix-generated output is treated as readonly unless you explicitly change a flag to make it editable (and you likely shouldn't)
  • Equally space efficient to traditional package management, as you store dependencies and their sources on disk to maintain atomicity and the ability to easily perform a rollback in system state

Nixpkgs is:

  • A repository of pre-written and bundled sets of Nix language code for installing applications without large amounts of work on the part of the user configuring their system(s) required
  • A binary cache for any given number of CPU architectures and operating systems, allowing for more efficient build process that can skip steps in cases where the full-on compilation can be guaranteed to build the identical output as the binary
  • A source repository for NixOS

NixOS is:

  • A Linux distribution
  • Managed from the kernel up via Nix, meaning the entire non-home directory parts of the system are treated as immutable
  • Designed for reproducibility and change tracking via a repository, ensuring that any machine being managed via the configuration will have identical settings and software, and that rollbacks are as simple as returning to a previous atomic state
